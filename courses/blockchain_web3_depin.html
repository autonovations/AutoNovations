Capítulo 1 · Fundamentos de Web3, Criptografía Asimétrica y Arquitectura Blockchain

La Web 3.0 representa la evolución hacia una internet descentralizada donde los usuarios son propietarios de sus datos, identidades y activos digitales sin depender de intermediarios centralizados. El núcleo tecnológico son las blockchains públicas que garantizan inmutabilidad, transparencia y consenso distribuido.

Ethereum EVM Solana / Rust ECDSA / secp256k1 SHA-256 / Keccak-256 Merkle Trees Proof of Stake

Criptografía Asimétrica (ECDSA)

Toda identidad en blockchain se construye sobre criptografía de curva elíptica. Una clave privada de 256 bits genera deterministamente la clave pública y la dirección Ethereum mediante la curva secp256k1.

┌────────────────────────────────────────────────────────────────────────────┐ │ PIPELINE DE IDENTIDAD BLOCKCHAIN (ECDSA secp256k1) │ │ │ │ [ Private Key 256-bit ] ──ECDSA──► [ Public Key (x,y) secp256k1 ] │ │ │ │ │ │ Nunca exponer Keccak-256 Hash │ │ │ │ │ [ Address = últimos 20 bytes ] │ │ 0x742d35Cc...bC4 → tu wallet │ │ │ │ Firma Digital: sig = ECDSA.sign(message_hash, private_key) │ │ Verificación: addr = ECDSA.recover(message_hash, signature) │ └────────────────────────────────────────────────────────────────────────────┘

EVM vs Solana: Comparativa de Arquitecturas

Ethereum EVM (Solidity)
Máquina virtual de stack 256-bit. EIP-1559 para gas. Lenguaje: Solidity / Vyper. Consenso: Proof of Stake (Gasper). ~12 segundos por bloque. Compatibilidad: L2 (Arbitrum, Optimism, zkSync).
Solana (Rust / SBF)
Arquitectura de cuentas paralelas con eBPF bytecode. Proof of History + Tower BFT. ~400ms por bloque, ~65,000 TPS. Lenguaje: Rust con el framework Anchor. Costos mínimos.

Árboles de Merkle y Verificación de Integridad

Los Merkle Trees permiten verificar la pertenencia de una transacción a un bloque sin descargar toda la blockchain. Cada nodo padre es el hash de sus dos hijos, formando una raíz criptográfica (Merkle Root) incluida en el bloque header.

python — Merkle Tree simplificado 
import hashlib

def sha256d(data: str) -> str:
    return hashlib.sha256(hashlib.sha256(data.encode()).digest()).hexdigest()

def merkle_root(txids: list) -> str:
    if len(txids) == 1:
        return txids[0]
    if len(txids) % 2 != 0:
        txids.append(txids[-1])  # duplicar último si cantidad impar
    pairs = [sha256d(txids[i] + txids[i+1]) for i in range(0, len(txids), 2)]
    return merkle_root(pairs)

txs = ["tx_a_hash", "tx_b_hash", "tx_c_hash", "tx_d_hash"]
print(f"Merkle Root: {merkle_root(txs)}")
# → Merkle Root: 3c1e2f... (raíz del bloque)
Dato clave: La dirección Ethereum se deriva de los últimos 20 bytes del hash Keccak-256 de la clave pública. Nunca se almacena la clave privada en la blockchain.
Cuestionario — Capítulo 1
1. ¿Qué algoritmo de firma digital utiliza Ethereum para generar y verificar identidades de wallet?
ECDSA (Elliptic Curve Digital Signature Algorithm) con secp256k1 garantiza firmas cortas y verificación eficiente. RSA requeriría claves de miles de bits para seguridad equivalente.
2. ¿Cuál es la principal ventaja de la arquitectura de cuentas paralelas de Solana vs el modelo EVM?
Proof of History crea un reloj criptográfico que permite ordenar eventos sin consenso sincrónico, habilitando paralelismo masivo en el procesamiento de transacciones.

Contrato ERC-20 con OpenZeppelin

OpenZeppelin provee contratos auditados y estándares de la industria. Los tokens ERC-20 son fungibles y permiten transferencias, aprobaciones delegadas y emisión controlada.

Solidity 0.8.20 — Token ERC-20 con Roles 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";
import "@openzeppelin/contracts/security/Pausable.sol";

contract AutoNovToken is ERC20, AccessControl, Pausable {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    uint256 public constant MAX_SUPPLY = 1_000_000 * 10**18; // 1M ANT

    event TokensMinted(address indexed to, uint256 amount, uint256 timestamp);

    constructor(address admin) ERC20("AutoNovToken", "ANT") {
        _grantRole(DEFAULT_ADMIN_ROLE, admin);
        _grantRole(MINTER_ROLE, admin);
        _grantRole(PAUSER_ROLE, admin);
        _mint(admin, 100_000 * 10**18); // Supply inicial
    }

    function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) whenNotPaused {
        require(totalSupply() + amount <= MAX_SUPPLY, "Max supply exceeded");
        _mint(to, amount);
        emit TokensMinted(to, amount, block.timestamp);
    }

    function pause() external onlyRole(PAUSER_ROLE) { _pause(); }
    function unpause() external onlyRole(PAUSER_ROLE) { _unpause(); }

    function _update(address from, address to, uint256 value) internal override whenNotPaused {
        super._update(from, to, value);
    }
}

Patrón Proxy Upgradeable (UUPS)

UUPS — Universal Upgradeable Proxy Standard (EIP-1822)
Separa lógica de contrato (implementación) del almacenamiento de estado (proxy). El proxy delega todas las llamadas a la implementación actual mediante delegatecall. Permite actualizar la lógica sin perder el estado ni la dirección del contrato.
┌─────────────────────────────────────────────────────────────────┐ │ UUPS PROXY UPGRADE PATTERN │ │ │ │ User → call() → [ Proxy Contract (storage + address) ] │ │ │ delegatecall │ │ [ Implementation V1 (logic) ] │ │ │ │ │ upgradeTo(V2_address) │ │ │ │ │ [ Implementation V2 (new logic) ] │ │ (mismo storage, misma proxy addr) │ └─────────────────────────────────────────────────────────────────┘
Collision de Storage: Al actualizar contratos mediante proxies, asegúrate de usar ERC-7201 (Namespaced Storage) para evitar colisiones de slots de almacenamiento entre versiones.
Cuestionario — Capítulo 2
1. ¿Cuál es la principal ventaja del patrón UUPS sobre un contrato monolítico no upgradeable?
El patrón Proxy conserva el estado del contrato (balances, mappings) y su dirección pública mientras actualiza la lógica subyacente mediante delegatecall a una nueva implementación.
2. En Foundry, ¿qué función permite ejecutar código como si fuera un address específico (simulación de identidad)?
vm.prank() de Foundry establece msg.sender para la próxima llamada, permitiendo simular transacciones como cualquier cuenta (admin, usuario, atacante) en tests de seguridad.

Smart Contract DePIN: Pagos Autónomos por Telemetría

Solidity 0.8.20 — DePIN Sensor Payment Contract 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract DePINSensorNetwork {
    struct SensorReading {
        uint256 timestamp;
        int256  temperature;  // x100 para evitar decimales
        uint256 co2Ppm;
        bytes32 dataHash;     // IPFS hash del payload completo
    }

    mapping(address => SensorReading[]) public sensorLogs;
    mapping(address => bool) public registeredSensors;
    
    uint256 public rewardPerReading = 0.0001 ether; // 0.1 mETH por lectura
    address public immutable owner;

    event SensorDataRecorded(address indexed sensor, bytes32 dataHash, uint256 reward);
    event SensorRegistered(address indexed sensor);

    modifier onlyRegistered() {
        require(registeredSensors[msg.sender], "Sensor not registered");
        _;
    }

    constructor() payable { owner = msg.sender; }

    function registerSensor(address sensor) external {
        require(msg.sender == owner, "Only owner");
        registeredSensors[sensor] = true;
        emit SensorRegistered(sensor);
    }

    function submitReading(int256 temp, uint256 co2, bytes32 dataHash)
        external onlyRegistered {
        sensorLogs[msg.sender].push(SensorReading({
            timestamp:   block.timestamp,
            temperature: temp,
            co2Ppm:      co2,
            dataHash:    dataHash
        }));
        // Micropago automático al sensor
        if (address(this).balance >= rewardPerReading) {
            payable(msg.sender).transfer(rewardPerReading);
        }
        emit SensorDataRecorded(msg.sender, dataHash, rewardPerReading);
    }

    receive() external payable {} // permite financiar el contrato
}

SIWE: Sign-In with Ethereum para Hardware

Sign-In with Ethereum (EIP-4361) permite autenticación criptográfica usando wallets de dispositivos. En lugar de usuario/contraseña, el dispositivo firma un mensaje con su clave privada almacenada en el Secure Element o TPM chip.

Python — SIWE: Verificación de Firma de Dispositivo 
from eth_account import Account
from eth_account.messages import encode_defunct
from web3 import Web3

def create_siwe_message(device_address: str, nonce: str) -> str:
    return (
        f"autonovations.io wants you to sign in with your Ethereum account:\n"
        f"{device_address}\n\n"
        f"Sensor DePIN authentication\n\n"
        f"URI: https://api.autonovations.io/depin\n"
        f"Version: 1\n"
        f"Chain ID: 137\n"  # Polygon Mainnet
        f"Nonce: {nonce}\n"
        f"Issued At: 2026-07-28T10:00:00Z"
    )

def verify_device_signature(message: str, signature: str) -> str:
    msg = encode_defunct(text=message)
    recovered = Account.recover_message(msg, signature=signature)
    return Web3.to_checksum_address(recovered)

# Servidor verifica que la dirección recuperada == DID registrado
message   = create_siwe_message("0x1a2b...sensor", nonce="abc123xyz")
signature = "0x..."  # Generada por el TPM del dispositivo IoT
verified_address = verify_device_signature(message, signature)
print(f"[+] Dispositivo autenticado: {verified_address}")
Hardware Security: Para producción, almacena la clave privada del dispositivo IoT en un TPM 2.0, ATECC608B (Microchip) o un módulo SE050 (NXP). Nunca en flash sin cifrar.
Cuestionario — Capítulo 4
1. ¿Qué problema resuelve SIWE (Sign-In with Ethereum) en sistemas DePIN con hardware IoT?
SIWE elimina servidores OAuth/IAM: el dispositivo firma un mensaje con su clave privada en el Secure Element, el servidor verifica la firma y autentica sin base de datos de contraseñas.

Capítulo 5 · Ciberseguridad & Auditoría de Smart Contracts

La auditoría de seguridad de smart contracts es crítica: los exploits en DeFi han generado pérdidas superiores a $3 billones USD históricamente. Los vectores de ataque más comunes incluyen reentrancy, flash loans y errores de control de acceso.

Reentrancy Attack Flash Loan Exploit Integer Overflow Slither (Static Analysis) Mythril (Symbolic Exec.) Echidna (Fuzzer) Checks-Effects-Interactions

Vector 1: Reentrancy Attack (El DAO Hack, $60M USD)

Un contrato malicioso llama recursivamente a una función vulnerable antes de que el estado (balance) sea actualizado, drenando todos los fondos.

Solidity — VULNERABLE vs SEGURO (Reentrancy) 
// ❌ VULNERABLE — No actualiza balance antes de transferir
contract VulnerableVault {
    mapping(address => uint256) public balances;

    function withdraw() external {
        uint256 amount = balances[msg.sender];
        require(amount > 0);
        (bool ok,) = msg.sender.call{value: amount}(""); // ← Callback al atacante
        require(ok);
        balances[msg.sender] = 0; // ← Demasiado tarde: ya fue re-llamada
    }
}

// ✅ SEGURO — Patrón Checks-Effects-Interactions + ReentrancyGuard
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract SecureVault is ReentrancyGuard {
    mapping(address => uint256) public balances;

    function withdraw() external nonReentrant {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "No balance");
        balances[msg.sender] = 0; // ← EFFECTS primero
        (bool ok,) = msg.sender.call{value: amount}(""); // ← INTERACTIONS después
        require(ok, "Transfer failed");
    }
}

Vector 2: Flash Loan Exploit

Flash Loan Attack
El atacante toma prestados millones en una sola transacción sin colateral (flash loan de AAVE/Uniswap), manipula precios de oráculos en-chain, explota protocolos vulnerables, devuelve el préstamo y extrae la ganancia — todo en un único bloque atómico.
Casos reales: Beanstalk ($182M), Euler Finance ($197M), Compound ($150M). La mitigación principal es usar oráculos descentralizados como Chainlink en lugar de precios de liquidez en-chain manipulables.

Cuestionario — Capítulo 5
1. ¿Cuál es el patrón correcto para mitigar ataques de reentrancy en Solidity?

Mythril explora todas las rutas de ejecución posibles del bytecode EVM de forma simbólica, identificando estados que llevan a vulnerabilidades según el SWC Registry (Smart Contract Weakness Classification).
